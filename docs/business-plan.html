1. Executive Summary

ZeroClaw on SpacetimeDB is a hosted platform that allows developers and businesses to deploy and run multi-agent AI systems without managing infrastructure. Users bring their own LLM API keys (OpenAI, Anthropic, etc.), while we provide the real-time, scalable backend using SpacetimeDB's database-integrated compute.

The service targets developers who want the power of ZeroClaw's agent framework combined with SpacetimeDB's built-in state synchronisation, multi-tenancy, and low operational overhead.

Key Value Proposition

  • No servers to manage — SpacetimeDB Cloud handles everything.
  • Real-time multi-agent coordination out of the box.
  • Users pay only for infrastructure (storage & compute) — LLM costs are theirs.
  • Predictable, low monthly cost starting at $25 for up to 120M reducer calls.

2. Product Overview

The platform hosts ZeroClaw agents inside SpacetimeDB. Each agent runs as a set of reducers (transactional state functions) and procedures (I/O-capable functions), and communicates with external LLMs via SpacetimeDB's ctx.http.

Core Components

  • SpacetimeDB-Native Memory: Agent memories stored in the memories table with keyword-based recall. Each memory is scoped to an agent_id with category tagging (core, daily, conversation).
  • Agent Isolation: Every table uses agent_id scoping plus owner: Identity fields enforced via ctx.sender in reducers. This provides per-agent data isolation.
  • LLM Integration: Procedures call LLM APIs using ctx.http with user-supplied API keys. State is maintained atomically using with_tx blocks within procedures.
  • Real-Time Subscriptions: Clients subscribe to agent state changes (new messages, tool requests, task completion) via SpacetimeDB's built-in WebSocket subscriptions.
Technical Correction
Isolation is via agent_id + owner: Identity, not user_id. The current codebase uses SpacetimeDB's Identity type (cryptographic identity from ctx.sender) for ownership, and agent_id for data scoping. There is no user_id column. For a multi-tenant hosted platform, a tenant_id or account-level isolation layer would need to be added above the existing agent-level isolation.
Technical Correction
No embeddings in the current SpacetimeDB module. The original business plan mentions "embeddings" as part of the memory backend. The actual implementation uses keyword-based recall (string matching on words >3 chars) from the memories table, not vector embeddings. The main ZeroClaw codebase (src/memory/) does support embeddings via SQLite+vector, but the SpacetimeDB module does not. Adding embedding support would require either an external embedding API call in the recall path or a SpacetimeDB-native vector type.
Technical Correction
API keys are stored in plaintext in the POC. The code comments note "stored encrypted in production — plaintext here for POC" but no encryption is currently implemented. For a hosted platform, this is a critical gap. Options: use SpacetimeDB's planned secret storage, implement application-level encryption (e.g., ChaCha20-Poly1305 as the main ZeroClaw codebase does), or store keys in an external secret manager and pass references.

Current Status: MVP code is complete for core orchestration. Encryption, tenant isolation, and embedding-based recall are identified as pre-launch requirements for a hosted service.

Key Technical Decisions (with rationale)

  • SpacetimeDB Pro Tier ($25/month): Provides 100,000 TeV/month (~120M reducer calls), enough for thousands of active users.
  • Procedures for LLM calls: Use SpacetimeDB's "unstable" feature to enable ctx.http for outbound HTTP inside procedures. Atomicity maintained via with_tx blocks for interleaved state reads/writes.
  • Storage at $1/GB/month: Allows generous per-user memory (e.g., 50 MB/user costs only $0.05/user/month).
Technical Correction
Procedures use "unstable" feature, not "beta". The Cargo.toml specifies spacetimedb = { version = "2.0", features = ["unstable"] }. This is a SpacetimeDB feature gate, not a general beta label. The ProcedureContext type (which provides ctx.http) is only available with this feature. The original plan's reference to "beta feature" should be understood as "unstable API that may change between SpacetimeDB versions."
Technical Correction
Atomicity model is with_tx, not full-procedure transactions. Unlike reducers (which are fully transactional), procedures use explicit ctx.with_tx(|tx| { ... }) blocks for table operations. Each with_tx block is atomic, but the procedure as a whole is not — HTTP calls between with_tx blocks can fail, leaving partial state. The orchestration loop handles this by storing messages incrementally and using status fields (pending/completed/failed) for recovery.

Additional Risk Identified
API key storage without encryption. The current POC stores LLM API keys in plaintext in the agents table. Since all tables are marked public (subscribable), any connected client could theoretically read other agents' API keys via table subscriptions. This is a launch-blocking security issue for a hosted platform. Mitigation: (1) Remove public from the agents table, (2) encrypt API keys at rest, (3) only decrypt inside procedures, never expose via subscriptions.
Additional Risk Identified
All tables are public (subscribable by any connected client). In the current implementation, every table uses #[spacetimedb::table(name = ..., public)]. For a hosted multi-tenant platform, this means any connected user could subscribe to and read all agents' data, memories, conversations, and security policies. Mitigation: Use SpacetimeDB's private table visibility combined with row-level security checks, or implement a gateway layer that filters subscriptions per tenant.
Improvement Note
Add a rate limiter to process_message(). The security_policies table has a rate_limit_per_minute field, but the current orchestration loop doesn't enforce it. For a hosted platform with free-tier users, this would be essential to prevent abuse and control costs.

  • Implement referral program.

Phase 4: Growth (Month 2–6)

  • Iterate based on feedback.
  • Add features: team accounts, analytics dashboard, custom domains.
  • Explore partnerships with AI tool directories.
Improvement Note
Pre-launch security hardening is a prerequisite. Before any external users have access, the following must be completed: (1) Make agents table private (API keys), (2) Add tenant-level isolation above agent_id, (3) Enforce rate_limit_per_minute in the orchestration loop, (4) Add input validation/sanitization for tool parameters, (5) Implement API key encryption. These should be tracked as launch-blocking items, not post-launch improvements.
