The Database Is the Runtime

SpaceClaw's SpacetimeDB module replaces the traditional agent server with a single database that thinks, remembers, acts, and coordinates — all inside the data layer.

Before you dive in

SpacetimeDB Concepts Primer

SpaceClaw's SpacetimeDB runtime uses several concepts that may be unfamiliar. Here's a quick glossary so the rest of these docs make sense.

Concept What It Means
Table A typed database table, like a SQL table. All agent state (agents, messages, memories, tool requests) lives in tables. Tables are defined as Rust structs with the #[spacetimedb::table] macro.
Reducer A function that mutates table state transactionally. Think of it like a stored procedure that can only read/write tables — it cannot make outbound HTTP calls. Used for state management (create agent, store memory, update policy).
Procedure Like a reducer, but with access to ctx.http for outbound HTTP. This is why the orchestration loop (which calls the LLM API) runs as a procedure, not a reducer. Requires the SpacetimeDB "unstable" feature.
Subscription A real-time WebSocket push mechanism. Clients subscribe to a table (or filtered rows) and receive instant updates when rows change. The worker uses subscriptions to watch for new tool requests and pending sends.
Identity A cryptographic identity assigned to each connected client. Used for ownership tracking (who owns an agent) and worker registration. Available as ctx.sender in reducers/procedures.
ctx.http The HTTP client available only inside procedures. Supports GET/POST with headers and body. This is how the server calls LLM APIs, sends Telegram messages, and executes HTTP-based tools — all from inside the database.

For comprehensive SpacetimeDB documentation, see spacetimedb.com/docs.

What we built
🧠

Brain-in-the-Database

The entire agent orchestration loop — LLM calls, memory recall, tool dispatch, channel sends — runs as SpacetimeDB procedures. No application server needed for HTTP-only workflows.

🔧

Thin Local Worker

A minimal Rust binary handles only what the database can't: shell execution, filesystem access, and hardware peripherals. Everything else stays inside SpacetimeDB.

🔒

Security as Data

Per-agent security policies live in a table — deny-by-default, tool allowlists/blocklists, autonomy levels, rate limits. Policy changes are instant row updates, not redeployments.

👥

Multi-Tenant by Default

Every agent is rows in shared tables, not a separate deployment. Add a new agent with one reducer call. Real-time sync between agents is free via SpacetimeDB subscriptions.

How it flows

Message Lifecycle

From user input to agent response — the happy path through the system.

  User Message
       │
       ▼
  ┌─────────────────────────────────────────────┐
  │  process_message()  [SpacetimeDB Procedure]  │
  │                                             │
  │  1. Store message in messages table         │
  │  2. Auto-save to memories table             │
  │  3. Build context: system prompt            │
  │     + recalled memories + chat history      │
  │  4. Call LLM API via ctx.http              │
  │  5. Parse response                          │
  │     ├─ No tools → Send response, done      │
  │     ├─ HTTP tools → Execute inline, loop   │
  │     └─ Local tools → Write request rows    │
  └─────────────────────────────────────────────┘
       │                              │
       │ completed                  │ awaiting_local_tools
       ▼                              ▼
  Channel Send              ┌──────────────────────┐
  (Telegram/Discord/       │  Worker picks up      │
   Slack/Webhook)          │  pending requests     │
                           │  → executes locally   │
                           │  → submits results    │
                           └──────────┬───────────┘
                                      │
                                      ▼
                           continue_conversation()
                              resumes the loop
Reference

Status Codes & State Machines

The system uses several status fields across tables. Here is a unified reference for every status value and its meaning.

ProcessResult.status

Returned by process_message() and continue_conversation() to indicate what happened.

Status Meaning What To Do
completed Agent finished reasoning. Final response is in the response field. Display to user. No further action needed.
awaiting_local_tools Agent needs local tool results (shell, file I/O). Requests have been written to local_tool_requests. Worker picks up requests, executes them, calls submit_local_tool_result(), then continue_conversation().
error Something failed: agent not found, LLM API error, parse failure. Check the response field for error details. Fix and retry.
iteration_limit Agent hit max_tool_iterations without producing a final response. Consider increasing the limit or simplifying the task.

LocalToolRequest.status

Tracks the lifecycle of a tool request dispatched to the worker.

  pending  ──worker claims──▶  processing  ──execution──▶  completed
                                            │
                                            └──on error──▶  failed

PendingSend.status

Tracks outbound messages queued for non-HTTP channel delivery.

  pending  ──worker delivers──▶  sent
                │
                └──on error──▶  failed
Why this shape

Design Principles

Each decision was driven by SpaceClaw's core goals.

Performance — LLM I/O inside DB eliminates network hops
Simplicity — Two components, not five microservices
Security — Policy is data, deny-by-default, per-agent isolation
Extensibility — New tools = table rows, not code deploys
Multi-tenancy — Agents are rows, not infrastructure
Observability — Every state change is a table mutation (subscribable)

Get running

Quickstart Guide

Go from zero to a working agent in five steps. This guide assumes a fresh machine.

Prerequisites

Dependency Minimum Version Install
Rust toolchain 1.78+ curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
SpacetimeDB CLI 2.0+ curl -sSf https://install.spacetimedb.com | sh
wasm32 target — rustup target add wasm32-unknown-unknown
LLM API key — An API key from Anthropic, OpenAI, or any OpenAI-compatible provider

Step 1: Start SpacetimeDB locally

$ spacetime start
info: Starting SpacetimeDB on 127.0.0.1:3000...
info: SpacetimeDB is ready.

This starts the local SpacetimeDB instance that will host the agent module.

Step 2: Publish the server module

$ cd spacetime/server
$ spacetime publish zeroclaw
info: Building module...
info: Published module "zeroclaw"
info: Module is running at ws://127.0.0.1:3000

This compiles the server to WebAssembly and deploys it into SpacetimeDB. The init() reducer runs automatically, creating the default agent and security policy.

Step 3: Set your LLM API key

$ spacetime call zeroclaw update_agent \
    --arg 1 \
    --arg '{"api_key": "your-api-key-here"}'

The default agent (ID 1) starts with an empty API key. You must set it before the agent can call an LLM. Without this step, every message will return an error.

Step 4: Generate bindings and start the worker

$ cd spacetime/server
$ spacetime generate --lang rust --out-dir ../worker/src/module_bindings --project-path .

$ cd ../worker
$ SPACETIME_URI=ws://localhost:3000 \
  SPACETIME_MODULE=zeroclaw \
  ZEROCLAW_AGENT_ID=1 \
  cargo run

info: Connected to zeroclaw at ws://localhost:3000
info: Registered worker "my-hostname"
info: Registered 3 local tools: shell, file_read, file_write
you> _

The worker connects to SpacetimeDB, registers its local tools (shell, file_read, file_write), and enters CLI mode where you can chat with the agent.

Step 5: Send a test message

you> Hello, what can you do?

agent> I'm SpaceClaw, an autonomous agent. I can:
  - Search the web (web_search)
  - Make HTTP requests (http_request)
  - Store and recall memories (memory_store, memory_recall)
  - Execute shell commands (shell)
  - Read and write files (file_read, file_write)

  How can I help you?

If you see a response from the agent, the full system is working: SpacetimeDB received your message, called the LLM, and returned the result through the worker.
