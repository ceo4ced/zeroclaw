1. Workspace Structure

The SpacetimeDB runtime is a Rust workspace with two crates under spacetime/.

spacetime/
  Cargo.toml              # workspace root
  server/
    Cargo.toml            # zeroclaw-brain (cdylib for SpacetimeDB)
    src/
      lib.rs              # ~1500 lines — entire server module
  worker/
    Cargo.toml            # zeroclaw-worker binary
    src/
      main.rs             # ~390 lines — thin I/O bridge
      module_bindings/    # auto-generated by `spacetime generate`
📦 spacetime/server/Cargo.toml Server dependencies 
[package]
name = "zeroclaw-brain"
version = "0.1.0"
edition = "2021"

[lib]
crate-type = ["cdylib"]     # SpacetimeDB loads this as a dynamic library

[dependencies]
spacetimedb = { version = "2.0", features = ["unstable"] }  # procedures require unstable
serde = { version = "1", features = ["derive"] }
serde_json = "1"
log = "0.4"
Why cdylib? SpacetimeDB modules compile to a shared library (.so/.dylib) that the SpacetimeDB host loads at runtime. The "unstable" feature enables ProcedureContext with ctx.http for outbound HTTP calls from inside the database.

All runtime state is encoded as SpacetimeDB tables. The #[spacetimedb::table] macro generates the schema, indexes, and CRUD operations.

/// An agent identity: model config, system prompt, limits.

/// Available tools and their JSON schemas.
#[spacetimedb::table(name = tool_registry, public)]
pub struct ToolRegistryEntry {

    pub description: String,
    pub parameters_schema_json: String,

}
Design note: Every table is marked public, making it subscribable by workers and external clients via SpacetimeDB's real-time protocol. The execution_mode field on ToolRegistryEntry is the key routing decision — it determines whether a tool runs inline in a procedure or gets queued for the worker.

5. State Management Reducers

Reducers are transactional state mutations. Each one is a single atomic operation.

📄 spacetime/server/src/lib.rs Selected reducers 
/// Register a local tool (called by worker on startup).
#[spacetimedb::reducer]
pub fn register_local_tool(
    ctx: &ReducerContext,
    name: String,
    description: String,
    parameters_schema_json: String,
) {
    // Upsert: delete existing then insert
    if let Some(existing) = ctx.db.tool_registry().name().find(&name) {
        ctx.db.tool_registry().name().delete(&name);
    }
    ctx.db.tool_registry().insert(ToolRegistryEntry {
        name,
        description,
        parameters_schema_json,
        execution_mode: "local".into(),  // worker-executed
    });
}

/// Worker submits result of a local tool execution.
#[spacetimedb::reducer]
pub fn submit_local_tool_result(
    ctx: &ReducerContext,
    request_id: u64,
    result: String,
    success: bool,
) {
    if let Some(mut req) = ctx.db.local_tool_requests().id().find(&request_id) {
        req.status = if success {
            "completed".into()
        } else {
            "failed".into()
        };
        req.result = result;
        req.claimed_by = ctx.sender.to_hex();
        ctx.db.local_tool_requests().id().update(req);
    }
}

/// Upsert persistent memory for an agent.
#[spacetimedb::reducer]
pub fn store_memory(
    ctx: &ReducerContext,
    agent_id: u64,
    key: String,
    content: String,
    category: String,
    session_id: String,
) {
    // Delete existing by key (upsert)
    if let Some(_) = ctx.db.memories().key().find(&key) {
        ctx.db.memories().key().delete(&key);
    }
    ctx.db.memories().insert(Memory {
        id: 0, agent_id, key, content, category, session_id,
        created_at: ctx.timestamp,
    });
}

6. process_message() — Main Entry Point

This procedure is the single entry point for all inbound messages. It stores the message, auto-saves to memory, and kicks off the orchestration loop.

📄 spacetime/server/src/lib.rs process_message procedure 
#[spacetimedb::reducer]  // procedure (uses ProcedureContext for ctx.http)
pub fn process_message(
    ctx: &ProcedureContext,
    agent_id: u64,
    channel: String,
    sender: String,
    content: String,
) -> ProcessResult {
    // 1. Look up agent
    let agent = match ctx.db.agents().id().find(&agent_id) {
        Some(a) => a,
        None => return error_result("Agent not found"),
    };

    // 2. Find or create conversation
    let conversation = find_or_create_conv(ctx, agent_id, &channel, &sender);

    // 3. Store the user message
    ctx.db.messages().insert(Message {
        id: 0,
        conversation_id: conversation.id,
        role: "user".into(),
        content: content.clone(),
        tool_call_id: String::new(),
        tool_calls_json: String::new(),
        created_at: ctx.timestamp,
    });

    // 4. Auto-save to memory (significant messages only)
    if content.len() > 20 {
        let mem_key = format!("conv_{}_msg_{}", conversation.id, ctx.timestamp);
        ctx_store_memory(ctx, agent_id, &mem_key, &content, "conversation");
    }

    // 5. Run the orchestration loop
    orchestration_loop(ctx, &agent, &conversation)
}
Key insight: ProcedureContext gives access to ctx.http for outbound HTTP. Regular ReducerContext only allows table operations. This is why the orchestration lives in a procedure, not a reducer.

7. orchestration_loop() — The Agent Brain

The core reasoning loop. Calls the LLM, dispatches tools, and loops until the agent has a final response or hits the iteration limit.

📄 spacetime/server/src/lib.rs Core orchestration loop (simplified) 
fn orchestration_loop(
    ctx: &ProcedureContext,
    agent: &Agent,
    conversation: &Conversation,
) -> ProcessResult {
    let max_iter = agent.max_tool_iterations as usize;
    let policy = ctx.db.security_policies().agent_id().find(&agent.id);

    for iteration in 0..max_iter {
        // ── Build LLM request ──
        let messages = build_messages(ctx, agent, conversation);
        let tools = build_tools(ctx);

        let request = LlmApiRequest {
            model: agent.model.clone(),
            messages,
            tools: if tools.is_empty() { None } else { Some(tools) },
            max_tokens: 4096,
        };

        // ── Call LLM API via ctx.http ──
        let body = serde_json::to_vec(&request).unwrap();
        let http_resp = ctx.http("POST", &agent.api_base_url)
            .header("content-type", "application/json")
            .header("x-api-key", &agent.api_key)
            .header("anthropic-version", "2023-06-01")
            .body(&body)
            .send();

        // ── Parse response ──
        let resp: LlmApiResponse = /* deserialize http_resp */;
        let content = /* extract text content */;
        let tool_calls = /* extract tool_calls array */;

        // Store assistant message
        ctx.db.messages().insert(Message {
            role: "assistant".into(),
            content: content.clone(),
            tool_calls_json: serde_json::to_string(&tool_calls).unwrap_or_default(),
            ..
        });

        // ── No tools? We're done ──
        if tool_calls.is_empty() {
            try_send_response(ctx, conversation, &content);
            return ProcessResult {
                status: "completed".into(),
                response: content,
                ..
            };
        }

        // ── Dispatch each tool call ──
        let mut local_pending: Vec<ToolCall> = Vec::new();

        for tc in &tool_calls {
            // Security check
            if !is_tool_allowed(&policy, &tc.name) {
                ctx.db.messages().insert(Message {
                    role: "tool".into(),
                    content: format!("Tool '{}' blocked by security policy", tc.name),
                    tool_call_id: tc.id.clone(),
                    ..
                });
                continue;
            }

            // Look up execution mode
            let tool_entry = ctx.db.tool_registry().name().find(&tc.name);

            match tool_entry.map(|t| t.execution_mode.as_str()) {
                Some("http") => {
                    // Execute inline — no worker needed
                    let result = execute_http_tool(ctx, &tc.name, &tc.arguments);
                    ctx.db.messages().insert(Message {
                        role: "tool".into(),
                        content: result,
                        tool_call_id: tc.id.clone(),
                        ..
                    });
                }
                Some("local") => {
                    // Queue for worker execution
                    ctx.db.local_tool_requests().insert(LocalToolRequest {
                        id: 0,
                        conversation_id: conversation.id,
                        tool_call_id: tc.id.clone(),
                        tool_name: tc.name.clone(),
                        parameters_json: tc.arguments.clone(),
                        status: "pending".into(),
                        result: String::new(),
                        claimed_by: String::new(),
                        created_at: ctx.timestamp,
                    });
                    local_pending.push(tc.clone());
                }
                _ => { /* unknown tool — store error message */ }
            }
        }

        // If any local tools are pending, pause and wait for worker
        if !local_pending.is_empty() {
            return ProcessResult {
                status: "awaiting_local_tools".into(),
                response: content,
                pending_local_tools_json: serde_json::to_string(&local_pending).unwrap(),
                ..
            };
        }

        // All HTTP tools — loop back to LLM
    }

    // Hit iteration limit
    ProcessResult { status: "iteration_limit".into(), .. }
}
Two-tier tool dispatch is the critical design decision. HTTP tools (web_search, http_request, memory) execute inline via ctx.http and feed results directly back to the LLM in the same loop iteration. Local tools (shell, filesystem) create LocalToolRequest rows and return immediately, pausing the loop until the worker picks them up and calls continue_conversation().

9. Security Policy Enforcement

📄 spacetime/server/src/lib.rs is_tool_allowed 
fn is_tool_allowed(policy: &Option<SecurityPolicy>, tool_name: &str) -> bool {
    let policy = match policy {
        Some(p) => p,
        None => return true,  // no policy = allow all
    };

    // Blocklist takes precedence
    let blocked: Vec<String> = serde_json::from_str(&policy.blocked_tools_json)
        .unwrap_or_default();
    if blocked.iter().any(|b| b == tool_name) {
        return false;
    }

    // Allowlist acts as whitelist (empty = all allowed)
    let allowed: Vec<String> = serde_json::from_str(&policy.allowed_tools_json)
        .unwrap_or_default();
    if !allowed.is_empty() && !allowed.iter().any(|a| a == tool_name) {
        return false;
    }

    true
}
Deny-by-default in practice: When the allowed_tools_json list is non-empty, only listed tools are permitted. The blocked list always wins — even if a tool appears on both lists, it's denied. This mirrors ZeroClaw's main codebase security philosophy.

10. Memory Recall & Context Injection

fn build_messages(
    ctx: &ProcedureContext,
    agent: &Agent,
    conversation: &Conversation,
) -> Vec<LlmMessage> {
    let mut out = Vec::new();

    // 1. System prompt
    out.push(LlmMessage {
        role: "system".into(),
        content: agent.system_prompt.clone(),
        ..
    });

    // 2. Inject recalled memories as system messages
    for mem in recall_context(ctx, agent, conversation) {
        out.push(LlmMessage {
            role: "system".into(),
            content: format!("[Memory: {}] {}", mem.key, mem.content),
            ..
        });
    }

    // 3. Conversation messages (limited by max_history_messages)
    let msgs: Vec<Message> = ctx.db.messages().iter()
        .filter(|m| m.conversation_id == conversation.id)
        .collect();
    let start = msgs.len().saturating_sub(agent.max_history_messages as usize);

    for msg in &msgs[start..] {
        out.push(/* convert Message to LlmMessage */);
    }

    out
}

fn recall_context(
    ctx: &ProcedureContext,
    agent: &Agent,
    conversation: &Conversation,
) -> Vec<Memory> {
    // Extract keywords from recent user messages
    let recent_msgs: Vec<Message> = ctx.db.messages().iter()
        .filter(|m| m.conversation_id == conversation.id && m.role == "user")
        .collect();

    let keywords: Vec<&str> = recent_msgs.last()
        .map(|m| m.content.split_whitespace()
            .filter(|w| w.len() > 3)
            .collect())
        .unwrap_or_default();

    // Search memories for keyword matches
    ctx.db.memories().iter()
        .filter(|m| m.agent_id == agent.id
            && keywords.iter().any(|kw|
                m.content.to_lowercase().contains(&kw.to_lowercase())))
        .take(5)  // inject up to 5 relevant memories
        .collect()
}

12. Worker — Local Tool Execution

The worker is a standalone Rust binary. It handles only what SpacetimeDB procedures can't: local shell and filesystem operations.

📄 spacetime/worker/src/main.rs Local tool dispatch + shell executor 
fn execute_local_tool(tool_name: &str, params_json: &str) -> String {
    match tool_name {
        "shell"      => execute_shell(params_json),
        "file_read"  => execute_file_read(params_json),
        "file_write" => execute_file_write(params_json),
        _ => format!("Unknown local tool: {}", tool_name),
    }
}

fn execute_shell(params_json: &str) -> String {
    #[derive(serde::Deserialize)]
    struct Params {
        command: String,
        #[serde(default = "default_timeout")]
        timeout_secs: u64,  // default: 30
    }

    let params: Params = serde_json::from_str(params_json)?;

    let output = Command::new("sh")
        .arg("-c")
        .arg(&params.command)
        .output();  // captures stdout + stderr

    match output {
        Ok(out) => {
            let stdout = String::from_utf8_lossy(&out.stdout);
            let stderr = String::from_utf8_lossy(&out.stderr);
            let mut result = stdout.to_string();
            if !stderr.is_empty() {
                result.push_str("\nstderr: ");
                result.push_str(&stderr);
            }
            // Truncate large output
            if result.len() > 8000 {
                result.truncate(8000);
                result.push_str("\n... (truncated)");
            }
            result
        }
        Err(e) => format!("Shell execution failed: {}", e),
    }
}

fn execute_file_read(params_json: &str) -> String {
    #[derive(serde::Deserialize)]
    struct Params {
        path: String,
        #[serde(default)]
        offset: usize,          // line offset (0-based)
        #[serde(default = "default_limit")]
        limit: usize,           // max 2000 lines
    }

    let content = std::fs::read_to_string(&params.path)?;
    let lines: Vec<&str> = content.lines().collect();
    let start = params.offset.min(lines.len());
    let end = (start + params.limit).min(lines.len());

    lines[start..end].iter()
        .enumerate()
        .map(|(i, line)| format!("{:>4} {}", start + i + 1, line))
        .collect::<Vec<_>>()
        .join("\n")
}

fn execute_file_write(params_json: &str) -> String {
    #[derive(serde::Deserialize)]
    struct Params { path: String, content: String }

    let params: Params = serde_json::from_str(params_json)?;
    std::fs::write(&params.path, &params.content)?;
    format!("Written {} bytes to {}", params.content.len(), params.path)
}
Safety boundaries: Shell output is capped at 8000 chars. File reads default to 2000 lines. These limits prevent the agent from overwhelming the LLM context with tool results. The worker also registers its local tools on startup so the server knows they exist and what parameters they accept.

    spacetime_uri: String,   // default: "ws://localhost:3000"
    module_name: String,     // default: "zeroclaw"
    agent_id: u64,           // default: 1
    mode: String,            // "cli" or "daemon"
    worker_name: String,     // default: hostname()
}

fn run_cli_mode(config: &WorkerConfig) -> Result<()> {
    // The full flow (SDK integration pending):
    //
    // 1. Connect to SpacetimeDB
    // 2. Register as worker + register local tools
    // 3. Subscribe to local_tool_requests (status = 'pending')
    // 4. Read user input
    // 5. Call process_message() procedure
    // 6. If "awaiting_local_tools":
    //      execute each tool, submit results, call continue_conversation()
    // 7. Print final response

    let stdin = io::stdin();
    loop {
        print!("you> ");
        let mut input = String::new();
        stdin.lock().read_line(&mut input)?;

        match input.trim() {
            "/quit" | "/exit" => break,
            cmd if cmd.starts_with('/') => handle_cli_command(cmd, config),
            msg => {
                // conn.procedures.process_message(
                //     config.agent_id, "cli", config.worker_name, msg
                // )
                println!("[Would call process_message]");
            }
        }
    }
    Ok(())
}

/// Tool definitions registered with SpacetimeDB on startup.
fn local_tools() -> Vec<(&static str, &static str, &static str)> {
    vec![
        ("shell",
         "Execute a shell command on the local system",
         r#"{"type":"object","properties":{"command":{"type":"string"}},"required":["command"]}"#),
        ("file_read",
         "Read a file from the local filesystem",
         r#"{"type":"object","properties":{"path":{"type":"string"}},"required":["path"]}"#),
        ("file_write",
         "Write content to a file on the local filesystem",
         r#"{"type":"object","properties":{"path":{"type":"string"},"content":{"type":"string"}},"required":["path","content"]}"#),
    ]
}
That's the entire runtime. Two Rust files. ~1500 lines for the server (all reasoning, state, and I/O coordination), ~390 lines for the worker (shell, filesystem, CLI). The server compiles to a SpacetimeDB module, the worker to a standalone binary. Together they form a complete autonomous agent with multi-tenant support, persistent memory, security policies, and multi-channel delivery.
