How the SpacetimeDB Runtime Works

Two-component architecture, data model, orchestration loop, security model, and deployment topology.

Component Architecture

The runtime is a Rust workspace with two crates. The server is a SpacetimeDB module containing all reasoning logic. The worker is a thin binary that handles local I/O.

Key insight: Conversations that only use HTTP tools (web search, API calls, memory) complete entirely inside SpacetimeDB with zero worker involvement. The worker is only needed for shell execution and filesystem access.

Orchestration Loop

The process_message() procedure is the main entry point. It runs the full agent reasoning loop inside SpacetimeDB.

process_message(agent_id, channel, sender, content)
  │
  ├─ Store user message in messages table
  ├─ Auto-save to memories (if content > 20 chars)
  │
  └─ orchestration_loop(ctx, agent, conversation)
       │
       for iteration in 0..max_tool_iterations:
       │
       ├─ build_messages()
       │    ├─ System prompt
       │    ├─ recall_context() → inject relevant memories
       │    └─ Conversation history (limited by max_history_messages)
       │
       ├─ build_tools() → tool definitions from tool_registry
       │
       ├─ POST to LLM API via ctx.http
       │    Request: { model, messages, tools, max_tokens }
       │    Response: { content, tool_calls[] }
       │
       ├─ Store assistant message
       │
       ├─ if no tool_calls:
       │    ├─ try_send_response() → HTTP channel send
       │    └─ return ProcessResult { status: "completed" }
       │
       └─ for each tool_call:
            │
            ├─ is_tool_allowed(policy, tool_name)
            │    ├─ blocked_tools list → DENY
            │    ├─ allowed_tools non-empty & not in list → DENY
            │    └─ otherwise → ALLOW
            │
            ├─ Lookup in tool_registry → execution_mode
            │
            ├─ if "http":
            │    ├─ execute_http_tool() inline
            │    ├─ Store result as role=tool message
            │    └─ continue loop (go back to LLM)
            │
            └─ if "local":
                 ├─ Insert LocalToolRequest row (status: pending)
                 ├─ Collect in local_pending list
                 └─ return ProcessResult { status: "awaiting_local_tools" }

Built-in HTTP Tools

These tools execute inline inside procedures using ctx.http — no worker needed.

web_search

Searches DuckDuckGo HTML results. URL-encodes the query, fetches first 2000 chars of the response page. No API key required.

http_request

Generic HTTP client. Supports GET/POST with custom body. Response truncated to 4000 chars. Used for API integrations.

memory_store

Upserts a key/value pair into the memories table. Supports categories: core, daily, conversation. Replaces existing entries by key.

memory_recall

Full-text keyword search across memories. Returns top 10 matches with key, content, and category. Used by the LLM to retrieve stored knowledge.

Local Tools (Worker-Executed)

These tools require the worker process because they access the local operating system.

ToolWhat it DoesSafety
shell Executes a command via sh -c. Captures stdout + stderr. 30s default timeout. Output truncated at 8000 chars.
file_read Reads a file with optional line offset and limit. Default limit: 2000 lines. Returns with line numbers.
file_write Writes content to a file path. Returns bytes written. Subject to security policy check.

Security Model

Per-agent security policies are stored in the security_policies table. The system is deny-by-default.

SecurityPolicy {
    agent_id:             u64,
    autonomy_level:       String,     // "manual" | "semi_auto" | "auto"
    allowed_tools_json:   String,     // JSON array — whitelist (empty = all)
    blocked_tools_json:   String,     // JSON array — blacklist (takes precedence)
    max_tool_iterations:  u32,
    rate_limit_per_minute:u32,
}

Authorization Logic

is_tool_allowed(policy, tool_name) → bool
  │
  ├─ tool in blocked_tools?        → DENY
  ├─ allowed_tools non-empty?
  │   └─ tool NOT in allowed_tools? → DENY
  └─ otherwise                      → ALLOW

Blocked list always wins. Then allowed list acts as whitelist.
Empty allowed list = all tools permitted (minus blocked).

Multi-Tenancy Isolation

  • Each agent has its own security policy, memories, and conversations
  • Agent ownership tracked via SpacetimeDB Identity
  • Workers are registered and tracked by identity
  • Tool authorization is checked per-call, per-agent

Channel Architecture

Channels route responses to messaging platforms. HTTP-capable channels are sent directly from procedures. Non-HTTP channels use the pending_sends table as a queue.

Direct HTTP Send (Procedures)

  • Telegram: POST to /bot{token}/sendMessage
  • Discord: POST to webhook URL with {"content": ...}
  • Slack: POST to webhook URL with {"text": ...}
  • Generic webhook: POST with {"target", "content"}

Queued Send (Worker-Assisted)

  • Fallback when no channel config is found
  • Used for non-HTTP channels (iMessage, IRC)
  • Worker subscribes to pending_sends table
  • Picks up pending rows and delivers locally

Memory Architecture

Memories persist across conversations. They're injected into the LLM context via keyword-based recall.

build_messages(ctx, agent, conversation) → Vec<LlmMessage>
  │
  ├─ "system": agent.system_prompt
  │
  ├─ recall_context(ctx, agent, conversation)
  │   ├─ Extract keywords from recent user messages (words > 3 chars)
  │   ├─ Search memories table for keyword matches
  │   └─ Inject top 5 as "system" messages: "[Memory: {key}] {content}"
  │
  └─ Recent conversation messages (limited by max_history_messages)
Auto-save: Every user message longer than 20 characters is automatically saved to the memories table with category "conversation". This ensures the agent builds context even without explicit memory_store calls.

Deployment Topology

# 1. Publish the server module
spacetime publish zeroclaw

# 2. Generate worker bindings
cd spacetime/server
spacetime generate --lang rust --out-dir ../worker/src/module_bindings --project-path .

# 3. Start the worker
SPACETIME_URI=ws://localhost:3000 \
SPACETIME_MODULE=zeroclaw \
ZEROCLAW_AGENT_ID=1 \
cargo run
API key required: After publishing, call the update_agent reducer to set the LLM API key and model for your agent. Without this, LLM calls will fail.
