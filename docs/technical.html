How the SpacetimeDB Runtime Works

Two-component architecture, data model, orchestration loop, security model, and deployment topology.

Component Architecture

The runtime is a Rust workspace with two crates. The server is a SpacetimeDB module containing all reasoning logic. The worker is a thin binary that handles local I/O.

Key insight: Conversations that only use HTTP tools (web search, API calls, memory) complete entirely inside SpacetimeDB with zero worker involvement. The worker is only needed for shell execution and filesystem access.

Orchestration Loop

The process_message() procedure is the main entry point. It runs the full agent reasoning loop inside SpacetimeDB.

process_message(agent_id, channel, sender, content)
  │
  ├─ Store user message in messages table
  ├─ Auto-save to memories (if content > 20 chars)
  │
  └─ orchestration_loop(ctx, agent, conversation)
       │
       for iteration in 0..max_tool_iterations:
       │
       ├─ build_messages()
       │    ├─ System prompt
       │    ├─ recall_context() → inject relevant memories
       │    └─ Conversation history (limited by max_history_messages)
       │
       ├─ build_tools() → tool definitions from tool_registry
       │
       ├─ POST to LLM API via ctx.http
       │    Request: { model, messages, tools, max_tokens }
       │    Response: { content, tool_calls[] }
       │
       ├─ Store assistant message
       │
       ├─ if no tool_calls:
       │    ├─ try_send_response() → HTTP channel send
       │    └─ return ProcessResult { status: "completed" }
       │
       └─ for each tool_call:
            │
            ├─ is_tool_allowed(policy, tool_name)
            │    ├─ blocked_tools list → DENY
            │    ├─ allowed_tools non-empty & not in list → DENY
            │    └─ otherwise → ALLOW
            │
            ├─ Lookup in tool_registry → execution_mode
            │
            ├─ if "http":
            │    ├─ execute_http_tool() inline
            │    ├─ Store result as role=tool message
            │    └─ continue loop (go back to LLM)
            │
            └─ if "local":
                 ├─ Insert LocalToolRequest row (status: pending)
                 ├─ Collect in local_pending list
                 └─ return ProcessResult { status: "awaiting_local_tools" }

End-to-End Example: A Real Conversation

To make the orchestration loop concrete, here is the exact sequence of events when a user asks the agent to search the web. This shows every JSON payload and table mutation along the way.

Scenario: "What is the population of Tokyo?"

Step 1: The user sends a message. The caller invokes the process_message procedure.

// Procedure call from worker or external client
process_message(
    agent_id: 1,
    channel:  "cli",
    sender:   "zeroclaw_user",
    content:  "What is the population of Tokyo?"
)

Step 2: The procedure stores the message, auto-saves to memory, and builds the LLM request. Here is the JSON body sent to the LLM API via ctx.http:

{
  "model": "anthropic/claude-sonnet-4-20250514",
  "messages": [
    { "role": "system", "content": "You are SpaceClaw, an autonomous agent..." },
    { "role": "user",   "content": "What is the population of Tokyo?" }
  ],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "web_search",
        "description": "Search the web via DuckDuckGo",
        "parameters": { "type": "object", "properties": { "query": { "type": "string" } } }
      }
    },
    // ... other tool definitions
  ],
  "max_tokens": 4096
}

Step 3: The LLM responds with a tool call (it wants to search the web):

{
  "content": "",
  "tool_calls": [
    {
      "id": "call_abc123",
      "type": "function",
      "function": {
        "name": "web_search",
        "arguments": "{\"query\": \"population of Tokyo 2025\"}"
      }
    }
  ]
}

Step 4: web_search is an HTTP tool. The procedure executes it inline via ctx.http (no worker involved):

// execute_http_tool makes this call inside SpacetimeDB:
GET https://html.duckduckgo.com/html/?q=population%20of%20Tokyo%202025

// Response (truncated to 2000 chars):
"Tokyo population 2025 - The population of Tokyo is approximately 13.96 million..."

Step 5: The tool result is stored as a role=tool message, and the loop calls the LLM again with the tool result included:

{
  "model": "anthropic/claude-sonnet-4-20250514",
  "messages": [
    { "role": "system",    "content": "You are SpaceClaw..." },
    { "role": "user",      "content": "What is the population of Tokyo?" },
    { "role": "assistant", "content": "",
      "tool_calls": [{ "id": "call_abc123", ... }] },
    { "role": "tool",      "content": "Tokyo population 2025 - ...",
      "tool_call_id": "call_abc123" }
  ],
  "max_tokens": 4096
}

Step 6: The LLM returns a final response with no tool calls. The procedure sends it to the channel and returns:

// LLM final response:
{
  "content": "The population of Tokyo is approximately 13.96 million people as of 2025, making it one of the most populous cities in the world.",
  "tool_calls": []
}

// ProcessResult returned to the caller:
{
  "status": "completed",
  "response": "The population of Tokyo is approximately 13.96 million...",
  "conversation_id": 1,
  "pending_local_tools_json": ""
}
Two LLM calls, zero worker involvement. Because web_search is an HTTP tool, the entire conversation completed inside a single SpacetimeDB procedure invocation. The procedure made two LLM API calls (one to get the tool request, one to get the final answer) and one DuckDuckGo search, all via ctx.http.

Built-in HTTP Tools

These tools execute inline inside procedures using ctx.http — no worker needed.

web_search

Searches DuckDuckGo HTML results. URL-encodes the query, fetches first 2000 chars of the response page. No API key required.

http_request

Generic HTTP client. Supports GET/POST with custom body. Response truncated to 4000 chars. Used for API integrations.

memory_store

Upserts a key/value pair into the memories table. Supports categories: core, daily, conversation. Replaces existing entries by key.

memory_recall

Full-text keyword search across memories. Returns top 10 matches with key, content, and category. Used by the LLM to retrieve stored knowledge.

Local Tools (Worker-Executed)

These tools require the worker process because they access the local operating system.

ToolWhat it DoesSafety
shell Executes a command via sh -c. Captures stdout + stderr. 30s default timeout. Output truncated at 8000 chars.
file_read Reads a file with optional line offset and limit. Default limit: 2000 lines. Returns with line numbers.
file_write Writes content to a file path. Returns bytes written. Subject to security policy check.

Worker Reconnection & Resilience

In production, network disruptions happen. Here is how the worker and SpacetimeDB handle connection loss and recovery.

Worker Lifecycle

Worker Start
  │
  ├─ Connect to SpacetimeDB via WebSocket
  │    └─ SpacetimeDB assigns cryptographic Identity
  │
  ├─ register_worker() reducer → inserts row in workers table
  │
  ├─ register_local_tool() × 3 → registers shell, file_read, file_write
  │
  ├─ Subscribe to local_tool_requests (status = 'pending')
  ├─ Subscribe to pending_sends (status = 'pending')
  │
  └─ Ready — processing tool requests as they arrive
       │
       │ (network disruption)
       ▼
  Disconnected
       │
       ├─ SpacetimeDB fires on_disconnect()
       │    └─ Removes worker row from workers table
       │
       └─ Worker detects disconnect
            └─ Reconnect with exponential backoff
                 └─ On success: re-register worker + tools + re-subscribe

What Happens to In-Flight Requests

ScenarioRequest StateRecovery
Worker disconnects before claiming a request Stays pending Another worker (or the same worker after reconnect) picks it up
Worker disconnects while executing (status = processing) Stuck as processing The hourly run_hygiene() scheduled task resets stale processing requests back to pending
Worker submits result then disconnects completed No issue — continue_conversation() has already been triggered
Stale request recovery is not instant. Requests stuck in processing state rely on the hourly hygiene cycle to be reset. In time-sensitive deployments, consider reducing the hygiene interval or implementing a manual reset_stale_requests() reducer.

Security Model

Per-agent security policies are stored in the security_policies table. The system is deny-by-default.

SecurityPolicy {
    agent_id:             u64,
    autonomy_level:       String,     // "manual" | "semi_auto" | "auto"
    allowed_tools_json:   String,     // JSON array — whitelist (empty = all)
    blocked_tools_json:   String,     // JSON array — blacklist (takes precedence)
    max_tool_iterations:  u32,
    rate_limit_per_minute:u32,
}

Authorization Logic

is_tool_allowed(policy, tool_name) → bool
  │
  ├─ tool in blocked_tools?        → DENY
  ├─ allowed_tools non-empty?
  │   └─ tool NOT in allowed_tools? → DENY
  └─ otherwise                      → ALLOW

Blocked list always wins. Then allowed list acts as whitelist.
Empty allowed list = all tools permitted (minus blocked).

Multi-Tenancy Isolation

  • Each agent has its own security policy, memories, and conversations
  • Agent ownership tracked via SpacetimeDB Identity
  • Workers are registered and tracked by identity
  • Tool authorization is checked per-call, per-agent

Security Policy Configuration Examples

The set_security_policy reducer lets you configure per-agent security postures at runtime. Here are common patterns:

// Example 1: Read-only agent — can search and read, but cannot execute or write
set_security_policy(
    agent_id: 1,
    autonomy_level:       "semi_auto",
    allowed_tools_json:   "[]",                              // allow all by default
    blocked_tools_json:   "[\"shell\", \"file_write\"]",      // block dangerous tools
    max_tool_iterations:  5,
    rate_limit_per_minute: 20,
)

// Example 2: Restricted research agent — only web search and memory
set_security_policy(
    agent_id: 2,
    autonomy_level:       "auto",
    allowed_tools_json:   "[\"web_search\", \"memory_store\", \"memory_recall\"]",
    blocked_tools_json:   "[]",
    max_tool_iterations:  8,
    rate_limit_per_minute: 30,
)

// Example 3: Public-facing agent — strict rate limit, no local tools
set_security_policy(
    agent_id: 3,
    autonomy_level:       "manual",
    allowed_tools_json:   "[\"web_search\", \"http_request\"]",
    blocked_tools_json:   "[\"shell\", \"file_read\", \"file_write\"]",
    max_tool_iterations:  3,
    rate_limit_per_minute: 5,
)

Autonomy Levels Explained

LevelBehaviorUse Case
manual Tool calls are logged but execution requires explicit confirmation via the approval mechanism. The orchestration pauses until a human (or supervisor agent) approves each tool call. High-risk environments, public-facing bots, compliance-sensitive tasks
semi_auto HTTP tools (web_search, memory) execute automatically. Local tools (shell, file_write) require confirmation. This is the default. Development, internal use, balanced risk/autonomy
auto All allowed tools execute without confirmation. The agent operates fully autonomously within its allowed/blocked tool boundaries. Trusted internal agents, automated pipelines, batch processing

Error Handling & Debugging

When things go wrong, here is how to diagnose common problems.

Common Error Scenarios

SymptomLikely CauseHow to Fix
ProcessResult returns status: "error" with "Agent not found" Invalid agent_id passed to process_message() Query agents table: spacetime sql zeroclaw "SELECT id, name FROM agents"
LLM returns empty or garbled response API key not set or invalid Call update_agent reducer to set a valid API key. Check SpacetimeDB logs for HTTP 401/403 errors.
Local tool requests stay pending forever No worker is connected or worker crashed Check workers table: spacetime sql zeroclaw "SELECT * FROM workers". Restart the worker if empty.
Tool call rejected with "blocked by security policy" Tool is in the agent's blocked_tools_json or not in allowed_tools_json Query security_policies for the agent and adjust allowed/blocked lists.
ProcessResult returns status: "iteration_limit" Agent exceeded max_tool_iterations without producing a final answer Increase max_tool_iterations on the agent, or simplify the task.
Channel message not delivered Channel config missing or incorrect credentials Check channel_configs table and pending_sends for failed rows.

Debugging with SpacetimeDB Logs

SpacetimeDB captures all log::info! / log::error! output from the module. Use the CLI to read them:

# View recent logs
spacetime logs zeroclaw

# Follow logs in real time (like tail -f)
spacetime logs zeroclaw -f

# Check the state of stuck tool requests
spacetime sql zeroclaw "SELECT id, tool_name, status, created_at FROM local_tool_requests WHERE status != 'completed' ORDER BY created_at DESC"

# Inspect recent process results for errors
spacetime sql zeroclaw "SELECT id, status, response FROM process_results ORDER BY id DESC LIMIT 5"
Debugging tip: If a conversation seems stuck, check three things in order: (1) Is a worker connected? Query workers. (2) Are there pending tool requests? Query local_tool_requests. (3) Did the last ProcessResult return an error? Query process_results.

Channel Architecture

Channels route responses to messaging platforms. HTTP-capable channels are sent directly from procedures. Non-HTTP channels use the pending_sends table as a queue.

Direct HTTP Send (Procedures)

  • Telegram: POST to /bot{token}/sendMessage
  • Discord: POST to webhook URL with {"content": ...}
  • Slack: POST to webhook URL with {"text": ...}
  • Generic webhook: POST with {"target", "content"}

Queued Send (Worker-Assisted)

  • Fallback when no channel config is found
  • Used for non-HTTP channels (iMessage, IRC)
  • Worker subscribes to pending_sends table
  • Picks up pending rows and delivers locally

Channel Configuration Guide

The channel architecture routes messages to platforms, but each channel must be configured first. Channel configs are stored in the channel_configs table and created via the configure_channel reducer.

ChannelConfig Table Structure

ChannelConfig {
    name:          String,   // unique key, e.g. "telegram", "discord-ops"
    channel_type:  String,   // "telegram" | "discord" | "slack" | "webhook"
    credential:    String,   // bot token, webhook URL, or API key
    api_base_url:  String,   // base URL for the platform API
    extra_json:    String,   // additional config as JSON (optional)
}

Configuring Telegram

// 1. Get a bot token from @BotFather on Telegram
// 2. Register the channel:
configure_channel(
    name:         "telegram",
    channel_type: "telegram",
    credential:   "7123456789:AAHfiqksKZ...",    // your bot token
    api_base_url: "https://api.telegram.org",
    extra_json:   "{}",
)

// The agent will POST to: https://api.telegram.org/bot{token}/sendMessage
// Messages arrive when process_message is called with channel="telegram"

Configuring Discord

// 1. Create a webhook in your Discord channel settings
// 2. Register the channel:
configure_channel(
    name:         "discord",
    channel_type: "discord",
    credential:   "https://discord.com/api/webhooks/123/abc...",
    api_base_url: "",    // not needed for webhooks — URL is the credential
    extra_json:   "{}",
)

// The agent will POST {"content": "..."} to the webhook URL

Configuring Slack

// 1. Create an Incoming Webhook in Slack App settings
// 2. Register the channel:
configure_channel(
    name:         "slack",
    channel_type: "slack",
    credential:   "https://hooks.slack.com/services/T00/B00/xxxx",
    api_base_url: "",
    extra_json:   "{}",
)

// The agent will POST {"text": "..."} to the webhook URL
Fallback behavior: If a conversation's channel name has no matching entry in channel_configs, the response is written to the pending_sends table instead. The worker (or another client) can subscribe to this table and deliver the message through any custom transport.

Memory Architecture

Memories persist across conversations. They're injected into the LLM context via keyword-based recall.

build_messages(ctx, agent, conversation) → Vec<LlmMessage>
  │
  ├─ "system": agent.system_prompt
  │
  ├─ recall_context(ctx, agent, conversation)
  │   ├─ Extract keywords from recent user messages (words > 3 chars)
  │   ├─ Search memories table for keyword matches
  │   └─ Inject top 5 as "system" messages: "[Memory: {key}] {content}"
  │
  └─ Recent conversation messages (limited by max_history_messages)
Auto-save: Every user message longer than 20 characters is automatically saved to the memories table with category "conversation". This ensures the agent builds context even without explicit memory_store calls.

Observability & Monitoring

Every state change in SpaceClaw is a table mutation, which means you can monitor the entire system by subscribing to tables. Here is how to observe what the agent is doing.

Key Tables to Watch

TableWhat to MonitorAlert Condition
local_tool_requests Tool execution queue depth and status Rows stuck in pending or processing for > 5 minutes
pending_sends Outbound message delivery queue Rows stuck in pending (no worker to deliver them)
process_results Agent response status and errors High rate of error or iteration_limit statuses
workers Connected worker instances Worker count drops to zero
messages Conversation throughput Useful for auditing and analytics

Subscribing to Tables for Real-Time Monitoring

Any SpacetimeDB client can subscribe to table changes via WebSocket. Subscriptions receive instant push notifications when rows are inserted, updated, or deleted.

// Rust SDK subscription example (conceptual)
let conn = SpacetimeDbClient::connect("ws://localhost:3000", "zeroclaw").await?;

// Subscribe to all tool requests with filtering
conn.subscribe("SELECT * FROM local_tool_requests WHERE status = 'pending'").await?;

// Handle real-time updates
conn.on_insert::<LocalToolRequest>(|_ctx, row| {
    log::info!("New tool request: {} ({})", row.tool_name, row.id);
});

conn.on_update::<LocalToolRequest>(|_ctx, _old, new| {
    if new.status == "failed" {
        log::error!("Tool request {} failed: {}", new.id, new.result);
    }
});

Hygiene & Automatic Cleanup

The run_hygiene() scheduled task runs every hour and performs automatic cleanup:

  • Removes local_tool_requests rows with status completed older than 1 hour
  • Removes pending_sends rows with status sent older than 1 hour
  • Resets processing requests from disconnected workers back to pending
  • Cleans up stale process_results entries
External monitoring integration: Set up a dedicated agent with a webhook channel config pointing to your monitoring system (PagerDuty, Slack alerts, etc.). Write a simple subscription client that watches for error conditions and calls process_message() to alert the monitoring agent.
